# Report every completed polling run

A Sender-side per-type Projection Refusal retry starts or coalesces into an ordinary manual Polling Run and grants that type one-time priority through the existing fair scheduler. Its normal per-type Sync Checkpoint outcome records success, repeated block, failure, or progress; no retry-specific run kind, trigger, control message, or Portal-to-Sender command is added.

Before reading, the Sender durably opens one identified Polling Run. It enqueues one encrypted, byte-stable Sync Checkpoint when that run finishes, not one per record type; after process recovery, it first closes any persisted open run as interrupted and checkpoints it before beginning another. A checkpoint records its run sequence, trigger, Sender wall-clock times, monotonic elapsed duration when available, the allowlisted Background Scheduling Status observed for that run, each type's not-due, no-change, progressed, completed, deferred, blocked, not-permitted, failed, or interrupted outcome and allowlisted health-data-free reason, a separate source-data-staged flag, and outbox message and byte counts sampled before the checkpoint is inserted. It contains no source-record counts, source tokens, Source Identities, health dates, or health values. A scheduled run continues while collection is disabled: queued delivery proceeds, no Health Connect read begins, every affected type reports deferred with reason collection-disabled, and the run still checkpoints. It receives the same strict ordering, retry, and Delivery Receipt semantics as every Outbox Message. Portal receipt time, not the Sender clock, determines Polling Freshness; Sender times remain diagnostic claims, and implausible skew creates a visible health-data-free condition without rejecting the message. Polling Freshness and Last Delivery are scoped to one Sender Installation and never carry across replacement. Before the active installation has an accepted checkpoint, Polling Freshness is never-reported rather than calculated from enrollment; the Portal presents this neutrally, labels an open run or accepted delivery as first-poll-in-progress, and makes the state action-required only after 24 hours from Sender activation. Afterward Polling Freshness is current through six hours, delayed after six hours, and stale after 24 hours, while Last Delivery separately records the Portal receipt time of its latest accepted data or control message. The Portal labels Background Scheduling Status as the last report with its receipt time and never treats it as guaranteed current; stale Polling Freshness makes that observation stale too. Staleness or restricted or unexpectedly unregistered scheduling points the Operator to foreground manual sync and the Sender's setup guidance, but none of these states changes retained health results. When the Sender is running and detects such a scheduling restriction, it also raises a persistent local notification; v1 requests neither a battery-optimization exemption nor a foreground service. Acceptance updates Polling Freshness, Last Delivery when the checkpoint is newly accepted, and operational health without changing a Health Summary, Data Watermark, or Cutover Record. The Portal retains every accepted checkpoint indefinitely in the Operational Store and Operational Backups; Operations shows the latest state and paginated history, Portable Exports include only current polling state, and Diagnostic Bundles contain aggregates rather than raw checkpoint history. At most one source traversal runs per type, and a configurable cross-type pool defaults to two. Eligible types use a durable round-robin order: each completed page returns its type to the tail and persists the next priority so restart cannot repeatedly favor the same types. Eligibility is checked before claiming a slot; an ineligible type retains its place, records its exact lifecycle outcome and reason, and is skipped so healthy types proceed, then resumes at that retained position when the condition clears. Manual intent may move one type forward once without permanent bypass and never cancels active work; overlapping hourly, foreground, and manual triggers otherwise coalesce into one follow-up. A background trigger uses an eight-minute soft budget within WorkManager's ten-minute limit, stops starting new pages at that point, stages any active page atomically when possible, and reports progressed when pages remain; foreground and manual triggers may continue without that deadline. This adds non-health operational traffic and retains status behind any older blocked delivery in exchange for distinguishing a successful no-change check, an interrupted run, an inaccurate phone clock, a delivery without a poll, and a Sender that has stopped running.
