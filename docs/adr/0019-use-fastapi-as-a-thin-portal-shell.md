# Use FastAPI as a thin Portal shell

The Operations page and `portal` command are adapters over the same governed activation-review Interface for showing an exact transition report, confirming rejection, or approving and immediately activating a valid bound candidate; the Sender exposes none of these controls. The command also exposes read-only Portable Export verification through its governed Interface.

The Portal will use Python 3.14 or newer with FastAPI and Uvicorn as a thin ASGI seam, Jinja2 server-rendered templates, explicit CSRF protection for browser mutations, standard-library `sqlite3`, and ordered checksummed SQL migrations. Its five stable destinations are Overview, Records, Summaries, Sources, and Operations. Overview leads with separate Last Delivery and exact Polling Freshness for the active Sender Installation: never-reported until that installation has an accepted Sync Checkpoint, then current through six hours, delayed after six hours, or stale after 24 hours based on Portal receipt time. Never-reported is neutral setup state, an open run or accepted delivery adds first-poll-in-progress, and only 24 hours without a checkpoint after activation makes it action-required. A replacement installation never inherits the retired installation's values; enrollment time may appear separately without being treated as a poll. Sender backlog, collection-disabled state, the time-stamped last reported Background Scheduling Status, processing, storage, conflict, quarantine, unresolved-policy, and persistent reconciliation-failed trust state follow. Stale polling is prominent and directs the Operator to open the Sender and run manual sync but never invalidates retained health results. Compact provenance-aware cards then show today's Steps, latest completed Sleep, latest Weight, and recent Heart Rate range; the Portal adds no goals, scores, recommendations, or medical interpretation. Record detail owns provenance and Amendments; Sources owns origin inspection and Source Selection; Operations owns Sender state and full paginated Sync Checkpoint history, explicit Reconciliation Failure retry through the same reconciliation Interface as the `portal` command, processing health, exports, and deletion. Summary views default to 30 local days, offer inclusive 7-, 30-, and 90-local-date windows through today, a calendar-year window preserving leap-day behavior, and inclusive custom date ranges. They initially use daily points and preserve gaps and non-measured states rather than coercing them to zero. During ordinary refresh they retain the last trusted result only with a visible newer-evidence-pending or refresh-failed condition; an initial pending or failed result has no invented number. The browser also owns Fallback Timezone Policy confirmation. A `portal` command exposes backup creation, restore, migration, reconciliation retry, and Portal Diagnostic Bundle production. Routes and commands call the same governed modules instead of reimplementing rules. All reachable browser devices are trusted to read and mutate in v1: CSRF prevents hostile-site form submission but is not an account or login layer. A separately supervised worker owns durable Processing Jobs, Summary Refresh Jobs, and Export Jobs; FastAPI background callbacks and in-memory queues do not. This accepts a deliberately current Python runtime floor and Tailscale trust assumption in exchange for a lighter single-Operator system without Django's broader application framework.
