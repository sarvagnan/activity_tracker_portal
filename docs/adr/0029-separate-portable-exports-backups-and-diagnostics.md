# Separate portable exports, backups, and diagnostics

Each Export Job pins its package and record-schema versions when created. A newer worker that no longer supports that writer fails the job explicitly and directs the Operator to request a new export rather than silently changing its format. Before publishing, the producer verifies the complete artifact through the pure `portable-export-contract` Interface; a separate read-only `portal export verify <file>` adapter invokes the same Interface to check any artifact without importing it or mutating Portal state.

The verifier retains support for every released major independently of the current-major-only producer; removing a major requires an explicit format-deprecation decision, and unknown or deprecated majors receive named refusal rather than partial success. Verification uses only the selected artifact, shipped schemas, and safety limits, with no Operational Store, network, credentials, or persistent Portal mutation. Human output and optional stable `--json` output contain versions, file identities, counts, sizes, and named failures but no health values; exit `0` means every required check passed, `1` means invocation, filesystem, or internal verifier failure, `2` means an invalid package, manifest, checksum, schema, or entry, `3` means an unsupported or explicitly deprecated major, and `4` means a configured safety limit was exceeded. JSON uses matching stable status names and a deterministically ordered failure list.

RFC 8785 JSON Canonicalization Scheme defines the bytes of the manifest, metadata, and each authoritative NDJSON object. Object keys are unique, non-finite numbers are rejected, unsafe-width integers use schema-declared decimal strings, and every NDJSON object has exactly one following LF. Collections split by entity family and record type into deterministic 10,000-object parts ordered by stable domain identity and then revision or sequence; duplicate ordering keys fail production and verification rather than collapsing or gaining a byte-order tie-breaker. Every required collection appears in the manifest with its schema version, record count, and ordered part inventory; an empty collection has count zero and no parts, while omission is invalid. Safe ASCII schema slugs form `meta/<family>.json`, typed `data/<family>/<record-type>/part-000001.ndjson`, untyped `data/<family>/part-000001.ndjson`, and optional `csv/<family>/<record-type>.csv` paths beneath root `manifest.json`. The manifest alone assigns meaning and canonical path order, and convenience CSV remains non-authoritative.

Before trusting archive declarations, both producer and verifier default to at most 10 GiB of archive bytes, 100,000 entries, 50 GiB total uncompressed bytes, 2 GiB for one entry, 16 MiB for one NDJSON line, a 200:1 compression ratio, 240 UTF-8 bytes per path, and eight path segments. Local configuration may alter those ceilings explicitly, but the manifest cannot raise them; the producer applies the same configured limits before publication so it does not create an artifact its corresponding default verifier refuses.

Every non-manifest ZIP entry, including optional CSV and embedded documentation or schemas, has a classification and SHA-256 digest recorded as lowercase hexadecimal in `manifest.json`; the manifest cannot inventory itself. The Package ID is the SHA-256 of the canonical manifest bytes, is not embedded recursively in that manifest, is returned by production and verification, and identifies the complete package. Collection-level digests may compare authoritative data independently, but different included convenience bytes mean different packages. Each collection schema declares required, non-null, ascending compound ordering fields; verification recomputes strict ordering and rejects equality as duplicate-key. The compressed container is regular ZIP or ZIP64 with UTF-8 entry names and only Store or Deflate compression. ZIP64 and data descriptors are permitted, while encryption, split archives, unsupported methods, duplicate or unsafe paths, symlinks, hardlinks, devices, and other non-regular entries are refused; fixed entry order is required even though compression metadata and container bytes do not define identity.

With `--json`, verification writes exactly one RFC 8785 object followed by LF to stdout, with stable `status`, nullable `package_id`, detected package major, aggregate file and byte counts, and ordered failures. It emits no progress text on stdout; stderr is reserved for invocation or internal diagnostics and never contains health values.

Production names the artifact `activity-tracker-export-<UTC-capture-time>-<first-16-package-id-hex>.zip`, using compact time such as `20260905T143012Z`; the filename is informational and verification never trusts it. Generated slug segments match `[a-z0-9]+(?:-[a-z0-9]+)*`, contain at most 63 bytes, and six-digit positive part numbers begin at one. Empty, dot, dot-dot, backslash, control-character, Unicode, case-fold-colliding, reserved-name misuse, and unrecognized paths are invalid. Every package embeds the exact referenced JSON Schemas and a versioned format README under governed `schema/` and `docs/` paths, with classifications and hashes in the manifest; synthetic conformance fixtures remain in the repository and release bundle rather than entering personal exports.

Deployment configuration alone sets producer ceilings and default verifier ceilings. Explicit verifier invocation flags may raise or lower its local limits, but browser requests cannot override producer limits and the manifest can never raise either. Human and JSON verification results report effective limits and observed values; exceeding a local ceiling remains status `4`, meaning inspection refusal rather than evidence of structural invalidity.

Embedded schemas use JSON Schema Draft 2020-12 with stable project-owned URN `$id` values. A `$ref` may resolve only to a unique schema embedded in the same package and identified by the manifest; filesystem and network resolution are disabled, and missing, duplicate, or unknown referenced schemas make the package invalid. A collection digest is SHA-256 over the logical concatenation of its canonical NDJSON lines in declared order, including each terminating LF and ignoring part boundaries; the empty collection digest is SHA-256 of zero bytes. The manifest records each lowercase-hex collection digest beside its record count and ordered part inventory.

After archive-safety checks permit traversal, verification continues deterministically and reports the first 100 failures in manifest-path and line order, together with the total `failure_count` and `failures_truncated`; it stops immediately whenever continuing would exceed a safety limit or the container cannot be traversed safely. Server-side artifacts are stored under the durable Export Job identity and full Package ID, never under the download filename. The user-facing filename remains only `Content-Disposition` and download metadata, so truncation or repetition cannot overwrite an artifact; identical-package deduplication is not required.

The Portal will produce three distinct artifacts. A Portable Export is an Operator-requested interoperability artifact, not the automatic Sender Synchronization flow, a scheduled recovery mechanism, or a v1 Portal import format. Operational Backup is the supported restoration path; any later Portable Export import requires separately governed identity-collision, provenance, deletion-ledger, and publication semantics. A shared, pure `portable-export-contract` module owns package composition, schemas, manifest validation, version compatibility, documentation, and synthetic conformance fixtures; the effectful `produce-portable-export` integration module obtains one consistent Operational Store snapshot, invokes that interface, and publishes the artifact through a durable Export Job independently of the browser connection. Export Jobs have durable pending, running, ready, failed, or cancelled state, never overlap, and remain available even when synchronization is incomplete. Each execution or lease recovery discards temporary output, takes a fresh consistent snapshot, and records its actual capture time and database watermark rather than promising request-time state. The versioned, checksummed manifest covers database-independent authoritative JSON for every retained current, candidate, abandoned, or otherwise ineligible item, including every retained Cutover Target and activated, failed, or superseded Candidate Build with explicit publication standing, identity, terminal outcome, processor versions, and target linkage. It also includes provenance, Amendments, Abandoned Attempt Evidence, Reconciliation Absences distinguished from Source Retractions with their coverage and cutover provenance, interpretation policies, retained health-data-free Cutover Records, current polling state, and each type's snapshot state, accepted fragment-chain position, Data Watermark, and pending-work state. The package and every record schema carry explicit versions: unknown majors are rejected, while readers tolerate unknown optional fields within a supported major. The Portal produces only its current major; earlier schemas, documentation, and fixtures remain versioned so existing artifacts stay interpretable, but multi-version production waits for a concrete consumer. The manifest records the producing Portal version, complete schema inventory, checksums, and required versus optional files; published schema documentation and synthetic conformance fixtures are governed with the format. Logical identity comes from canonical uncompressed files, safe entry names, and per-file manifest checksums, not outer compressed bytes: entry order is fixed, duplicate, absolute, or traversal paths are rejected, extraction enforces size limits and checksums, and compliant compression encodings may differ. It excludes transient lease and retry mechanics, other health-bearing worker-attempt history, and historical Sync Checkpoints. Convenience CSV defaults to eligible current evidence and places candidate, abandoned, and reconciliation-absence evidence in separately named files so none is silently interpreted as a published health observation. Verified output is published atomically without overwriting an existing artifact. A completed plaintext export remains for up to seven days, may be deleted immediately, is excluded from backups, and may be evicted earlier under storage pressure; startup removes expired and incomplete artifacts. The UI warns that it contains health data, Tailscale protects browser transfer, and the Operator owns protection after download. An Operational Backup contains the complete SQLite database, including linked attempt history, every accepted Sync Checkpoint, Cutover Records, and the applicable Deletion Ledger, under the deployment-owned periodic encryption and retention workflow. A Diagnostic Bundle is constructed locally on either participant from typed, allowlisted versions, aggregate job and Sync Checkpoint counts and timings, states, randomized aliases, curated failure codes, and Cutover versions, reasons, times, and aggregate outcome counts; it never includes raw checkpoint history, is saved or shared manually, never uploaded automatically, and is never produced by scraping or heuristically redacting logs. Credentials, encryption keys, Sender secrets, raw exception strings, source identifiers, covered health dates, and health values are excluded. This duplicates some packaging logic in exchange for keeping synchronization, data portability, disaster recovery, and support evidence from inheriting one another's incompatible contracts.
