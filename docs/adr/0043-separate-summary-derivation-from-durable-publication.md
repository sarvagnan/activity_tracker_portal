# Separate summary derivation from durable publication

Concrete summary modules will remain deterministic calculations that return candidate Health Summaries without persistence effects; a separate `refresh-summary-state` integration module will lease durable work, load the exact generation and policy target, invoke the applicable calculation, and conditionally publish an immutable revision. Invalidations for one summary identity and target state coalesce behind a monotonically advancing evidence token. A result publishes only if its token is still current; otherwise it remains unpublished and one successor is rearmed for the newest evidence, preventing both lost updates and work storms. Processor upgrades build affected candidates before atomically activating their manifest and summary set, while Operator policy requests become visibly pending and activate with their successfully rebuilt interpretations and summaries. Ordinary synchronization retains previous results as newer-evidence-pending across all pages of one or more Change Cycles and atomically publishes the affected set only from the newest complete evidence token after every covered cycle has accepted completion and terminal processing; every cycle, receipt, processing result, and attempt remains retained, but intermediate unpublished candidates are discarded. When first-publication, Replacement Baseline, or Reconciliation Snapshot cutover work begins, it atomically freezes a Cutover Target at the newest then-completed evidence boundary and creates an append-only Candidate Build under named processor versions. It neither retargets nor waits for later or open Change Cycles; those remain pending for ordinary publication after the coherent cutover, preventing a continuously active Sender from starving activation. Only one Cutover Target may be active per affected record type; other policy, processor, replacement, or reconciliation requests queue in arrival order, while disjoint types may build concurrently. Explicit reconciliation retry may create a Candidate Build under a corrected processor version within its existing target but does not let an unrelated request overtake it; when necessary, its successful Compound Cutover also activates the matching successor Processor Generation without admitting unrelated changes. Each target and initial build identity commit before work is enqueued, lease recovery resumes that same build idempotently, and activation is one SQLite transaction selecting exactly one complete validated build and appending its Cutover Record. An uncertain process exit is resolved from committed selection and record state; otherwise the same activation safely retries. After any successful baseline or reconciliation cutover, one ordinary publication catches up through the newest then-completed evidence boundary before the next queued target starts, without waiting for an open cycle. That catch-up receives bounded transient retries and must reach a terminal outcome, but terminal failure does not deadlock the queue: the prior view remains `newer-evidence-pending` and `refresh-failed`, then the next target may start against evidence that includes the failed catch-up. Ordinary publication creates no Cutover Record; the three baseline or reconciliation activations do. An initial pending or failed state has no number. Candidate Builds and their terminal outcomes remain append-only and inspectable while their underlying evidence is retained, regardless of which build activates, while transient lease mechanics do not become domain evidence. Published summary history and retained builds participate fully in privacy deletion, trading additional storage and coordination for a small calculation interface, durable retries, coherent reads, and auditable change.
