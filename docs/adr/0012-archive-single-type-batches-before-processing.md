# Archive single-type batches before processing

Each source page will contain exactly one Health Connect record type from one bounded Initial Snapshot, Reconciliation Snapshot, or Change Cycle read. Its ordered projections or retractions are deterministically partitioned into as many numbered Ingest Batch fragments as required by the Portal's advertised record-count and uncompressed-byte limits. Every fragment and the next per-type cursor or token position commit together in one Sender transaction, or none do; one indivisible projection above the ceiling blocks the type rather than being split or dropped. Before the first page of either snapshot kind, a separate per-type changes token, snapshot identity, and initial chain state commit durably together. Every fragment carries its cycle identity, source-page index, fragment index, and hash-chain position. After the final fragment is durable, a separate Snapshot Completion with an explicit initial or reconciliation kind, or a Change Completion, carries the final source-page, fragment, and record counts and cumulative fragment-chain digest but no source cursor or token. Message identity and checksum cover the exact uncompressed UTF-8 JSON envelope; transport may apply gzip, but the Portal must decompress under strict limits, verify the uncompressed checksum, and archive those exact JSON bytes, so compression settings cannot alter identity. A Delivery Receipt means the data or completion envelope is durably archived, not that normalization succeeded: record-level failures become Quarantined Records, an identical retry returns the same receipt, and conflicting bytes, corrupt envelopes, retired Senders, unsupported schemas, or an incomplete completion chain create a machine-readable Delivery Block whose message remains retained for Operator action. This isolates permissions and recovery by type and prevents processing defects from causing endless Sender retries without silently discarding an undelivered message, losing an interruption, or falsely completing a cycle.
