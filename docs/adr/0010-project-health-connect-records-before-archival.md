# Project Health Connect records before archival

Projection Refusal retry authority remains on the Sender, which owns the saved Device-local source position. The Portal may display the affected record type and `projection-refusal` instruction to open the Sender, but it cannot remotely lift the block and no reverse command channel is introduced. The Sender's one per-type retry starts or coalesces into an ordinary manual Polling Run, receives one-time priority, still obeys permission, storage, concurrency, and fair-scheduling rules, and records its result through the normal per-type Sync Checkpoint outcome rather than adding a retry-specific protocol message or trigger.

Because Health Connect exposes typed records rather than a stable external byte format, the Kotlin native module will create each versioned, lossless Source Projection as finalized UTF-8 JSON bytes containing every public type field and metadata value, including identifiers, modification time, origin, recording method, Device details, timestamps, offsets, and provider and SDK versions. One deterministic `project-source-record` module owns this projection contract and is shared by distinct snapshot-page and change-page readers; their cursor, expiration, retraction, and failure contracts remain separate rather than hidden behind one observation interface. Each record type evolves under its own closed Source Projection schema: unknown or missing fields under a declared version are invalid rather than silently ignored. Integers that may exceed JavaScript's safe range use schema-declared decimal strings; bounded integers remain JSON numbers, finite floating values use shortest round-trippable decimal notation, non-finite values are refused, and timestamps use RFC 3339 with explicit offset or `Z` and retained source precision. If any record in a source page cannot be projected, the entire page is refused and its cursor or token is not advanced; a deterministic Projection Refusal blocks that type with the allowlisted health-data-free reason `projection-refusal`, while other types continue without spending later read slots on the identical page. The Sender persists its health-data-free refusal identity from record type, saved page position, projection-schema version, and projection-implementation version. A changed version tuple permits one automatic retry; explicit Operator intent permits one attempt under the same tuple; and an identical repeated refusal returns the type to blocked rather than making every Polling Run retry it. A genuinely transient Health Connect read failure instead reports failed and retries on the next eligible run. Corrected governed projection behavior rereads the same page, and an invalidated position follows the full Initial or Reconciliation Snapshot path rather than skipping the record. Kotlin returns successful page bytes with the tentative cursor to the TypeScript shell, which treats them as opaque, base64-encodes them inside the JSON envelope, and atomically stores that finalized envelope with the cursor through `expo-sqlite`. This prevents JavaScript coercion or reshaping while leaving orchestration and delivery in the portable shell. The Portal decodes and treats the exact projected bytes as the Raw Record and performs normalization later; a projection with no processor is retained as an Unmodeled Record, excluded from canonical and derived views, and replayable when processing is added. This accepts base64 overhead, page-level blocking, and explicit schema evolution in exchange for server-side reinterpretation without reacquiring phone data, silently skipping an unrepresentable record, or misrepresenting inaccessible Health Connect internals as “raw.”
