# Require receipt-bound Sender delivery

Version one will allow one active Sender Installation. Enrollment begins in the Portal with a short-lived, one-use QR or manual code containing its tailnet address; a new installation generates a durable opaque identity, presents a matching fingerprint, and remains inactive until the Operator confirms it. That identity identifies lifecycle state but is not an application credential: Authorized Ingress remains the v1 authority, so impersonation by another device already trusted at ingress is inside the declared deployment trust boundary. Normal replacement drains and retires the previous installation before activating the new one. An unavailable old Device requires explicit destructive retirement acknowledging possible unsent loss; a new installation then takes a full permitted-history snapshot and reconciles what the source still exposes. Ordinary unlinking likewise drains first, retires in the Portal, and only then destroys the local key and state.

The Sender retains every unacknowledged Outbox Message—whether a data-bearing Ingest Batch, Snapshot Completion, Change Completion, Sync Checkpoint, or capability acknowledgement—without time-based dropping and delivers messages strictly in sequence. Message identity is the Sender Installation, a monotonically increasing sequence, and SHA-256 of the exact uncompressed JSON bytes; the matching Delivery Receipt echoes that tuple. An identical retry returns the prior receipt, while the same sequence with different bytes creates a Delivery Block. A higher sequence after a genuine loss is accepted but its gap is surfaced rather than making all later recoverable data undeliverable; a Snapshot Completion whose claimed page chain contains such a gap is blocked rather than accepted. Protocol outcomes are receipt, retryable failure, or Operator-action-required Delivery Block; timeouts and unknown transport outcomes retry identical bytes, while a blocked head message remains intact and prevents later delivery. Synchronization is eventual: hourly background work plus foreground and manual triggers are attempts rather than a delivery deadline. This accepts phone-side storage, explicit lifecycle friction, and a catastrophic-loss limit in exchange for observable at-least-once delivery while an installation remains intact.
