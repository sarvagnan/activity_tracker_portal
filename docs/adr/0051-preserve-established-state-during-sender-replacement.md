# Preserve established state during Sender replacement

A newly enrolled Sender Installation still performs a per-type Initial Snapshot and pre-read-token catch-up, but when the Portal already has current results their completed pair is a Replacement Baseline rather than a first publication. The prior view remains current while candidate evidence is archived and processed. The replacement installation starts with independent Last Delivery and never-reported Polling Freshness rather than inheriting the retired installation's operational state. When replacement cutover work begins, `complete-replacement-baseline` atomically freezes its Cutover Target at the newest then-completed evidence boundary and creates an append-only Candidate Build; later completed cycles wait for ordinary post-cutover publication rather than repeatedly restarting replacement. It then atomically reconciles matching Source Identities across installations, adds new identities, activates affected summaries, and appends a Cutover Record; it never infers Reconciliation Absence across installations, so unmatched retired-Sender evidence remains retained and eligible. Integrity failure or incomplete work leaves the prior view current. This may preserve evidence no longer present on the replacement Device and expose cross-store duplicates for explicit source selection or reversible grouping, in exchange for never treating a different source installation's silence as deletion.
