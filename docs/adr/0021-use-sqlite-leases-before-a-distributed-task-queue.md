# Use SQLite leases before a distributed task queue

A separately supervised `portal-worker` will claim Processing Jobs, Summary Refresh Jobs, and Export Jobs from distinct SQLite queues using expiring leases, do work outside the claim transaction, and atomically record idempotent outcomes. Their scheduling and domain states remain separate while private lease machinery is shared. Processing and the summary refreshes it invalidates receive bounded priority so accepted records progress promptly, but fair scheduling guarantees an export cannot starve. Summary invalidations for the same identity and target coalesce behind an evidence token rather than multiplying work. A Cutover Target and its initial Candidate Build identity commit before related work is enqueued; expiry or process recovery resumes that exact build idempotently rather than inventing another target, and its activation transaction both selects the validated build and appends the Cutover Record. Migration, restoration, and deletion exclude conflicting worker activity instead of competing through job priority. Transient processing and refresh failures receive bounded retries with backoff, after which the Operator may create a new attempt against the latest ordinary evidence or an append-only successor Candidate Build against an existing Cutover Target where governed. Deterministic projection or validation failures create Quarantined Records, while deterministic derivation or invariant failures remain failed until corrected governed behavior explicitly reprocesses them; manual retry is not presented as a repair for identical deterministic inputs. Celery, Redis, RabbitMQ, and an external result backend are deferred because they would not make broker publication atomic with the receipt transaction and would leave authoritative SQLite work rows necessary anyway. A future distributed dispatcher may publish job IDs when multiple machines, independently scaled pools, routing, or measured contention justify the additional subsystem.
