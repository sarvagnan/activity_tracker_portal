# Split concrete processors and activate them by generation

Approval creates no durable approved-awaiting-worker state. The Operations page or `portal` command calls one governed approve-and-activate Interface that revalidates the exact Cutover Target, Candidate Build digest, proposed manifest, and transition report and immediately consumes the Activation Approval in the same short transaction as the selectors and Cutover Record; refusal stores no pending approval. The approval has no time expiry because those inputs are immutable and later evidence lies outside the target, but replacement of any bound input or intersecting deletion invalidates it. Immediately before confirmation, both adapters show processor and schema versions, target and build identities, manifest digest, and per-record-type counts grouped by old-to-new terminal outcome and expected or unexpected classification, without Source Identities, dates, or values. Explicit rejection requires confirmation, is terminal, and retains the build and old view: an ordinary upgrade requires a new target and build after releasing the queue, whereas a rejected Compound Cutover requires a successor build under its still-active Reconciliation Failure and target, or Start Fresh Reconciliation or deletion. Rejection creates no Cutover Record; the Candidate Build instead records terminal `rejected`, decision time, and bound transition-report digest, and an ordinary target records rejected while a Compound target remains active. Each approval or rejection uses a 15-minute, one-use review token bound to the exact report and requested action; only its digest is stored before use. Expiry requires a fresh report. Token consumption stores the committed outcome atomically and retains that outcome indefinitely, so an identical retry after an uncertain response returns the existing Cutover Record or rejection result, while a changed binding or mismatched action is refused. Multiple tokens with identical immutable bindings may coexist: the first valid transaction decides, later same-action submissions return that committed outcome idempotently, and later opposite-action submissions return a named already-decided conflict with the health-data-free committed outcome. Merely generating another identical report does not invalidate earlier unexpired tokens.

Source reconciliation, common interpretation rules, and each concrete record-type processor are distinct governed scopes; Steps, Heart Rate, Sleep Session, and Weight likewise receive distinct summary scopes behind shared summary and range contracts. One immutable global Processor Generation maps every supported record type to its active processor version; a successor reuses unchanged mappings and reprocesses only changed types. Automatic activation requires complete affected canonical and summary candidates plus expected per-Source-Record terminal outcome transitions, not merely equal aggregate counts. A completed valid reclassification may pause for health-data-free Operator approval, while a missing, failed, invalid, or incomplete result cannot be overridden. The processor manifest and affected summary revisions then activate in one transaction, leaving the complete prior view current on any failure. The sole combined exception is a Compound Cutover for explicit retry of a Reconciliation Failure: a complete validated Candidate Build under a corrected processor version may activate its reconciliation results and a successor Processor Generation together, reusing every unchanged type mapping; its Cutover Record names both reasons and selectors, and no unrelated upgrade or policy change joins it. The Compound Cutover prevalidates all work and atomically commits the generation selector, reconciliation selectors, affected summaries, and Cutover Record; failure before commit changes none of them, and an uncertain exit is resolved from the durable cutover identity before the same activation may retry. Expected transitions governed by the acceptance pack activate automatically, while completed valid but unexpected transitions require the same health-data-free Operator approval as an ordinary processor activation; incomplete or invalid work remains non-overridable. This increases scope count and temporary storage in exchange for type-specific acceptance oracles, explicit source conflicts, coherent review, and ordinary views that never mix processor or summary versions accidentally.
