# Make synchronization completion receipt-bound control messages

Each Initial Snapshot, Reconciliation Snapshot, and Change Cycle data fragment will carry its cycle identity, record type, source-page index, fragment index, and ordered hash-chain position. After every fragment is durable locally, the Sender will enqueue a separate encrypted, byte-stable Snapshot Completion or Change Completion containing final source-page, fragment, and record counts and the cumulative fragment-chain digest but no source cursor or token; Snapshot Completion uses one structural envelope with an explicit initial or reconciliation kind. Each completion receives the same ordered retry and Delivery Receipt semantics as data-bearing Outbox Messages. The Portal blocks rather than acknowledges a completion whose kind, identity, counts, order, or chain does not match durably archived fragments. A blocked original message is never rewritten, skipped, or force-accepted: corrected Portal code may validate an identical retry, while genuinely unrecoverable evidence requires explicit destructive Sender retirement or reset, leaves the archived cycle incomplete, and begins a new installation and Initial Snapshot. This adds control variants and severe recovery friction in exchange for executable proof that partial data cannot be declared complete without duplicating otherwise identical snapshot-completion validation.
