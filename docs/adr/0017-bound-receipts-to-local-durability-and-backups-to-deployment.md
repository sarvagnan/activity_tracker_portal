# Bound receipts to local durability and backups to deployment

A Delivery Receipt proves one fully committed local database copy; it does not wait for another machine or backup, so disk loss before the next snapshot remains a deployment availability risk. Backup creation captures SQLite and the applicable Deletion Ledger consistently, records schema and application metadata plus checksums, verifies the captured database, and atomically publishes either a valid new Operational Backup or nothing. Restore requires an inactive Portal and explicit confirmation. It first makes a verified safety backup of current state, restores into staging, verifies checksums and schema compatibility, applies the latest Deletion Ledger, validates the result, and only then swaps state atomically; any failure leaves the original state active and unchanged. The project provides these commands, integrity checks, expiry metadata, and deletion-state application, with a daily default and a strict 30-day retention maximum; deployment owns scheduling, destination, encryption credentials, redundancy, and pruning. This keeps receipt latency and the application boundary local while making backup correctness testable without embedding one deployment service.
