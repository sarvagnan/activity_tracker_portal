# Use Expo as a shell around native health adapters

The Sender will use an Expo/React Native development and production build—not Expo Go—as a cross-platform shell for enrollment, per-type permissions, sync and outbox state, the last Delivery Receipt, actionable blocks, manual sync, local diagnostics, and safe unlink, replacement, and reset flows. It will not present health records, summaries, Amendments, or analytical views; those belong to the Portal. Version 1 will ship for Android only. A project-owned Kotlin module remains authoritative for Health Connect Source Projections and non-exportable Keystore operations; iOS and its Swift/HealthKit adapter are deferred until there is a concrete need rather than included merely because the shell is portable. Encrypted data and control Outbox Message BLOBs plus applicable cursors and snapshot state commit through `expo-sqlite`, builds and signing can run locally without an Expo cloud dependency, and third-party health bridges are references rather than the lossless contract seam. Expo BackgroundTask supplies the v1 deferrable background scheduling adapter with a one-hour minimum interval; its JavaScript callback, foreground activation, and manual button all invoke the same durable synchronization module. Scheduling is inexact and contributes triggers rather than correctness: persisted Polling Runs, cursors, transactions, and Outbox Messages survive interruption, while the adapter may be replaced only if physical-device qualification shows unacceptable behavior. Restricted or unexpectedly absent registration is a persistent action-required Sender state, produces a local notification when detected while running, and is reported by the next Sync Checkpoint as a time-bound Background Scheduling Status rather than a claim about future availability; foreground and manual synchronization remain available, while v1 neither requests a battery-optimization exemption nor uses a foreground service. Each trigger Adapter supplies an execution budget through the same synchronization Interface: the background Adapter stops starting new pages after eight minutes, preserving two minutes of WorkManager's ten-minute limit for atomic staging and checkpointing, while foreground and manual Adapters are not subject to that soft deadline. An active page may finish and stage atomically, interruption remains recoverable, and a run with pages remaining reports progressed rather than false completion. At most one source traversal runs per record type, and a configurable cross-type pool defaults to two. Eligible types use durable round-robin order: after one completed page a type returns to the tail, and the next priority persists across process restart. Eligibility is evaluated before a slot is claimed, so missing permission, Delivery Block, collection-disabled, or another known precondition state keeps its ring position but is skipped and reported while healthy types proceed; clearing the condition resumes from that retained position. Manual intent may move one type forward once but cannot permanently bypass another type. Hourly, foreground, and manual triggers coalesce into one follow-up rather than spawning parallel reads; manual intent never cancels an in-flight read. Every completed polling run stages one receipt-bound, health-data-free Sync Checkpoint, including scheduled runs that perform delivery but defer all source reads because collection is disabled. This accepts a native bridge on each platform and inexact OS scheduling in exchange for sharing the genuinely portable shell.
