# Support all SDK health-and-fitness types but not PHR

The Sender will pin stable Health Connect `1.1.0` and implement a Source Projection for every health-and-fitness record type it exposes, including feature-gated and specialized types, while each remains an explicit Operator opt-in. Enabled types are archived even before the Portal has a canonical processor, so later interpretation normally requires only server work; types added by a future stable SDK still require a Sender release, and an alpha SDK requires a separate governed justification. The separate experimental Medical Records/PHR API is excluded because its clinical FHIR resources, category permissions, inventory, and snapshot-reconciliation model would expand the fixed wellness scope into a distinct subsystem.
